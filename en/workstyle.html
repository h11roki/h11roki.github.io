How I work

I decide what to adopt by the numbers, and I write down why. When data is wrong, I don't stop at fixing it; I make sure the same error can't get in again. This is how I've been working, both in my internship and on my personal projects.

01What I value

LLM output always looks plausible, so I decide what to adopt by the numbers, not by feel. I work the same way at my internship and on personal projects.

Decide how to measure before changing anything

Before starting on improvements, I build the evaluation set and the tooling to compare against it. I write down the adoption criteria before I measure.

shirube I noticed that even two unchanged, identical configurations came out "significantly different" at twice the nominal rate, so I switched to interleaved runs of the two configurations compared with a permutation test.

Be most skeptical when the numbers go up

A gain on the data used for tuning isn't necessarily a gain in production accuracy. I don't adopt an improvement I can't explain.

Internship A 14-row lookup table with no source, which we had added ourselves, accounted for about 2 pt of precision. In production it would change the answers for about 4,400 stores with no basis, so I removed it, knowing the number would drop.

Measure and roll back, even my own changes

I decide based not only on the new correct answers a change produces but also on the new errors it introduces. In PRs I report both, like "Correct +16 / Wrong −2".

Internship Two of my own changes to the LLM output format had increased response parse failures from 8 → 364 and from 2 → 29. I reverted them and traced both to a common cause: the calls did not enforce the JSON schema.

Write decisions down

Before implementing, I write the design options, and why I rejected the ones I didn't pick, in an ADR (architecture decision record).

shirube 99 ADRs (as of November 8, 2026). The 3 improvements I rejected are recorded too, with their numbers and reasons.

03Fix it, then block it at the entry point

Every fix to existing data ships together with a guard against recurrence. When I find an error, I count how many stores share the same cause and correct the existing data with a fix batch. At the same time, I add a guard at ingestion that rejects the same error, and fix the extraction or judgment logic that produced it.

  1. Measure the scopeFind every store with the same cause
  2. Fix existing dataA fix batch
  3. Block it at the entry pointA guard at ingestion
  4. Fix the sourceExtraction and judgment logic
  5. Compare before and afterBoth what got fixed and any new errors

So far I've fixed these the same way: phone number formats (forwarding numbers, extensions, +81), store names that were just a place name or had an address mixed in, coordinates, business hours with every day closed, opening dates with dropped digits, business types that shouldn't be treated as stores, and large numbers of stores linked to a single URL.

04Count errors by cause

Let the counts decide where to fix. The judgment records keep the stage that dropped a value and the evidence it used, the reasons the LLM rejected each candidate, and the actual type of any exception, so errors are sorted mechanically into four causes. Since I can see how many cases each fix would move, I start where the count is highest.

  • No evidence
  • Never a candidate
  • Dropped at judgment
  • Resolved to a different entity

05Compare each change before and after on the same stores

Count both what became correct and what newly went wrong. I compare before and after a change on the same stores with the same criteria, and report both in the PR, like this. Simply rerunning the same code flips the results for dozens of stores, so I compare only stores whose fetched pages were the same before and after.

06What rules decide, and what I leave to the LLM

If the condition can be written down, it's a rule; if it takes reading context, it's the LLM. Anything whose conditions can be stated clearly, such as phone number and date formats, excluding corporate-registry sites, and merging companies by corporate number, is handled with rules. Judgments that require reading context, such as in what capacity a company appears on a page (operating company, job-ad recruiter, or facility management company), go to the LLM, and I pass it the evidence it needs. The LLM writes its reasoning before its answer, and that order is pinned by tests.

Rules

Conditions that can be stated clearly

  • Normalizing formats: phone numbers, dates
  • Exclusion rules: corporate-registry sites
  • Entity resolution: one company per corporate number

LLM

Judgments that require reading context

  • Reading a company's role: operator, recruiter, management company
  • Passing it evidence: registry, page field, domain
  • Reason → answer order: pinned by tests

07Trace the cause all the way to the monitoring gap

Why weren't stores growing? I looked at both the data and the system. When the store data seemed to have stopped growing, I checked the creation date of every row and pinned down that not a single new store had been created since a certain point. I also pointed out that daily monitoring counted only status changes, so it was built in a way that couldn't notice when collection stopped. I reconstructed the range that had been searched from the old collector's search terms, and laid out which business types hadn't been searched yet and an estimate of how many stores could be recovered.

  1. Count creation datesAcross every row
  2. Pin down when it stoppedZero new rows created
  3. Flag the monitoring gapIt counted only status changes
  4. Propose next stepsUnsearched business types and expected recovery

08Working with AI

AI provides the speed; I decide what to adopt. I hand much of the investigation and implementation to Claude Code. I run separate analysis sessions in parallel, one per symptom (wrong answers, over-extraction, misses), and I write the premises every session reads: definitions, how numbers are computed, and the unit of reporting. I have the AI cite the data rows behind each conclusion, have a separate session verify it independently, and send back anything without support. Once, a bug the AI said affected 66 cases turned out, when checked, to affect 1.

I decide which conclusions to adopt, and record the reasoning, the rejected alternatives and the measured values in the PR description.

10Database and API design

I also work on the production database and API (TypeScript, PostgreSQL) that receive the pipeline's output.

A

Manual store registration: allow NULL, keep the unique constraint

Check whether the quickest fix slips past the existing safety nets.

  • The Google Maps identifier was required and unique, but manual registration inserted the same empty string every time, so every registration after the first one failed
  • I rejected inserting a dummy value after finding that it would slip past three safety nets that check whether the identifier is empty, and send invalid, billed requests to an external API
  • PostgreSQL's UNIQUE doesn't treat NULLs as duplicates of each other, so I made the identifier nullable and kept the unique constraint
Read more
Approach
The pipeline's input type required the identifier and rejected unknown keys, so I fixed the deploy order as pipeline → DB and split the work into 5 PRs. For detecting duplicate registrations, I judged it cheaper to catch resubmissions under the same store name with an exact match that the existing index can serve (matching the input in both full-width and half-width forms) than to maintain a new partial-match index over millions of rows.
B

A social-media schema migration that never stops downstream

Migrate so that, at every point, everything still works from the old column alone.

  • Social media accounts were stored together as an array in a single column, so a partial update that found only Instagram wiped out X
  • Compared with consolidating them into a single JSON column (complex to read from, and hard to enforce types in the DB), I added three per-platform columns
  • Downstream still reads the old column, so I kept it as a complete list, and copied the values over with an idempotent batch that can resume midway
Read more
Problem
Locks and source URLs could also be held only once across all social media platforms, so a hand-corrected value got overwritten together with an update to a different platform.
Approach
I moved reads and writes over in this order: copy batch → admin UI → validation tool → producer side (expand / contract). I also changed the domain check used for classification from substring matching to suffix matching, correcting 1,826 misclassified URLs.
  • Address normalization gave different results across three ingestion paths; I consolidated it into one path in four stages. In the last stage, the pipeline switched to sending the address components, which made re-normalization on the DB side unnecessary.
