Evaluating an LLM pipeline: 100 stores in 48 s, the same result every time

Problem
Every change I tried meant waiting 2–3 hours to evaluate 900 stores at 20-way parallelism. External calls (search, crawling, LLM) made the results nondeterministic, so I couldn't tell whether a before/after difference came from the change.
What I did
Designed and implemented record/replay: external calls are recorded per service client, and during evaluation the network is blocked and responses come from the recordings. It also runs in CI on every PR.
Result (measured)
100 stores scored in 48 s at 8-way parallelism, with zero outbound connections and the same result on every run. After a code change, only the cache-missed calls are re-recorded (20 stores: 232 s, versus 942 s for the initial recording).

02Record, then replay with the network blocked

Run the same processing as production, as many times as needed, without leaving the machine. External calls that affect the result (search, crawling, the LLM, address matching, and so on) are made for real just once and recorded. During evaluation, the network is blocked, results are served from the recordings, and the output is scored. Scoring also runs as a CI job on every PR, so each change can be compared before and after on the same stores.

  1. RecordMake each external call for real, just once
  2. ReplayBlock the network and serve results from the recordings
  3. ScoreScore by corporate number match
  4. Run on every PRA CI job compares on the same stores every time

03The lookup key is "the inputs that determine the result"

Look up by service, method, and inputs, not by URL. An earlier prototype matched only on URL at the HTTP layer, so when a call sent a different address to the address-matching service, it returned the result for the previous address. I made each external service's client the unit of recording and keyed recordings on (service, method, inputs that determine the result), so this kind of mix-up can't happen.

For LLM recordings, the key also includes a hash of the prompt template (system, user, and output schema). I verified that changing one piece of wording turns only that call into a cache miss and gets it re-recorded.

Lookup keys
KeyResult
URL only (prototype)Returned the result for a different address
Service, method, inputs that determine the resultReturns the same result only for the same inputs
+ prompt hashOnly the calls whose wording changed miss the cache and are re-recorded

04Don't let missing recordings fail silently

Stop on what must stop; don't freeze transient failures into the recordings. The existing code had many places that catch an exception and fall back to a default. If a call missing from the recordings were swallowed there, it would be treated as a fetch failure and show up as a change in precision. I made the exception that signals a missing recording a subclass of BaseException, so it always halts the run.

Transient failures such as 503s and timeouts, on the other hand, are not frozen into the recordings; the store is marked "incomplete" and picked up in the next re-recording. I ported the existing scorer (TypeScript, zero tests) to Python and wrote tests for each rule.

How calls are handled
CaseHandling
Call not in the recordingsStop immediately (BaseException subclass)
Transient failure (503, timeout)Don't record it; re-record that store
Error page returned by the siteRecord it as content

05For the remaining gap, measure the breakdown to choose the next step

Target: 1 minute. On CI: 79 s. Locally, 20 stores run in about 30 s, but on CI it takes 79 s, short of the 1-minute target. Accumulating a breakdown with timers showed that 62% of the time went to HTML parsing, and 65% of that was re-parsing the same HTML. Raising parallelism from 8 to 12 didn't make it faster (the workers compete for CPU), so the next step is a change that reuses parse results.

One evaluation run on CI79 s target: 60 s
  • ~40%Re-parsing the same HTML (65% of parsing). The next change targets this
  • ~22%Other HTML parsing
  • 38%Everything else

At first, my review document said "80% of the time is in one function," but that was an error caused by profiler overhead. Re-measured with timers, it was 20%, and I corrected it before submitting for review.

06Running on real data to shake out bugs

Be the first to doubt what you built. Running on production data uncovered bugs in the record-and-replay mechanism itself.

Bugs found and how I fixed them
BugFix
A Unicode line separator (U+2028) in page text split recording lines partway throughChanged to split only on newlines (\n)
The replay process tried to connect to the cloud metadata service at import timeFixed so nothing goes outside during replay
During a week waiting for review, the development branch moved ahead by 32 commits and the way reference master data was loaded changedMoved the recording point outside the loading function, rebased the 7 PRs, and re-recorded only the cache-missed calls (232 s, versus 942 s to record from scratch)
+

Missing results in full evaluation runs

Fix both the other side's outage and our own weak spot.

  • In a full evaluation run (submitted 200 stores at a time), 35 of the 200 stores in one batch came back with no result
  • By connecting to an open port and a closed port at the same time, I pinpointed within 1 minute that the internal crawling API had stopped accepting connections (18.3% of TCP connections got no response to SYN), and reported it to the owner
  • On our side, a long timeout also applied to connection setup, so retries never kicked in; I split the connect and read timeouts so that a stalled call no longer stalls the whole run
