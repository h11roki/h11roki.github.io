仕事の進め方

数字で採否を決め、判断を残す。データの誤りは直すだけでなく、同じ誤りを二度と入れない。インターンと個人開発で続けている進め方です。

01大切にしていること

LLM の出力はもっともらしく見えるので、感覚ではなく数字で採否を決めています。仕事でも個人開発でも同じ進め方です。

測り方を、直す前に決める

改善を始める前に、評価データと比べる道具を作ります。採る条件は、測る前に書いておきます。

shirube　何も変えていない設定どうしでも「差あり」が名目の 2 倍出ると気づき、2 つの設定を交互に流して並べ替え検定で比べるように直した。

数字が上がったときほど、疑う

改善に使ったデータで上がった数字は、本番の精度とは限りません。理由を説明できない改善は採りません。

インターン　自分が承認して入れた出典のない 14 行の対応表が、精度の約 2pt を作っていたので、数字が下がるのを承知で外した（精度改善の 04）。

自分の変更でも、測って戻す

増えた正解だけでなく、新しく生んだ誤りも数えて採否を決めます。

インターン　抽出漏れを減らそうと検索語を広げた自分の変更は、増えた正解より新しく生んだ誤りの方が多かったので、自分で戻した。

判断を、文章で残す

設計の選択肢と、採らなかった理由を、実装より先に ADR（設計判断の記録）に書きます。

shirube　例：関係のない授業が増えるのを承知で、網羅を優先した判断（ADR 0080）。採らなかった改善 3 件も、数字と理由を残している。

02修正の例

精度の改善だけでなく、本番の店舗データに入った誤りを直す仕事も担当しています。誤りを 1 件見つけたら、同じ原因の店舗を数えて直し、取り込みと生成の側でも同じ誤りが入らないようにします。

誤り直したこと
開業日の取り違え記事の公開日や商業施設の開業日を、店舗の開業日として取っていた。日付の要素を除き、施設の開業日を弾くガードと登記系サイトの除外を入れた（社内の精度検証で 45.7% → 90.4%）
取り込みで正しい値を消す店舗の一括取り込み API（Next.js）で、「まだ取れていない（null）」と「該当なし（空配列）」を区別し、取れなかっただけで既存の値を消さないようにした。手で直してロックした値も上書きしない
全曜日が定休の営業時間既存の 102 件を空に戻し、取り込み時に同じ値を弾くガードを入れた

店舗の属性を抽出する LLM パイプラインの精度（2026 年 5 月〜7 月）

開業日・客席数・駐車場・決済手段の誤りを型に分けて対処しました（記事の公開日や入居施設の開業日の取り違え、法人登記サイトの日付の誤採用、全角数字の取りこぼしなど）。

社内の精度検証の値（運営会社の特定とは別の採点。母集団・時点はプロパティごとに異なる）
プロパティ精度 改善前 → 後カバレッジ 改善前 → 後
開業日45.7 → 90.4%28.7 → 70.0%
客席数73.0 → 94.0%67.0 → 80.8%
駐車場75.0 → 91.4%54.3 → 72.5%
決済手段47.0 → 90.8%32.4 → 78.0%

検索 API を単価約 17 分の 1 の API に移し、検索費用を 1 店舗あたり 1.4 円から 0.08 円にした。

03直して、入口でも止める

既存データの修正と再発防止を、必ず組で入れる。誤りが見つかったら、同じ原因の店舗がどれだけあるかを数え、修正のバッチで既存のデータを直します。同時に、取り込み時のガードで同じ誤りを弾き、誤りを生んだ抽出や判定の処理も直します。

  1. 範囲を数える同じ原因の店舗を洗い出す
  2. 既存データを直す修正のバッチ
  3. 入口で止める取り込み時のガード
  4. 発生源を直す抽出・判定の処理
  5. 前後を比べる直った件数と新しい誤りの両方

これまでに、電話番号の表記（中継番号・内線・+81）、地名だけの店名や住所が混ざった店名、座標、全曜日が定休の営業時間、開業日の桁落ち、店舗として扱わない業種、1 つの URL への大量の紐づけを、この形で直しました。

04変更は、同じ店舗で前後を比べる

正しくなった件数と、新しく生んだ誤りの両方を数える。同じ店舗・同じ基準で変更の前後を比べ、PR には次のように両方を書きます。

正解 +16／誤り −2

誤りの原因の分け方と、非決定性（実行ごとの揺れ）の切り離し方は、精度改善のページに書いています。

05ルールで決めるもの、LLM に任せるもの

条件を書けるものはルール、文脈を読むものは LLM。電話番号や日付の表記、登記系サイトの除外、法人番号での名寄せのように、条件をはっきり書けるものはルールで処理します。ページの会社がどの立場で載っているか（運営会社か、求人の募集主か、施設の管理会社か）のように文脈を読む判断は LLM に任せ、判断の材料を渡します。LLM の出力は理由を先に書かせ、その順序はテストで固定しています。

ルール

条件をはっきり書けるもの

  • 表記の正規化：電話番号・日付
  • 除外の条件：登記系のサイト
  • 名寄せ：法人番号で 1 社に

LLM

文脈を読む判断

  • 会社の立場を読む：運営・募集主・管理会社
  • 判断材料を渡す：登記・欄・ドメイン
  • 理由 → 答えの順：テストで固定

06原因を、監視の穴まで追う

店舗が増えない理由を、データと仕組みの両方から。店舗のデータが増えていないように見えたとき、全行の作成日を調べて、ある時期から新しい店舗が 1 件も作られていないと特定しました。日次の監視が状態の変化しか数えておらず、収集が止まっても気づけない作りだったことも指摘しました。旧収集の検索語から検索した範囲を復元し、まだ検索していない業種と、回収できる店舗数の見込みを示しました。

  1. 作成日を数える全行の作成日
  2. 止まった時期を特定新規作成が 0 件
  3. 監視の穴を指摘状態の変化しか数えていない
  4. 次の手を示す未検索の業種と回収の見込み

07AI との分担

速さは AI に、どれを採るかは自分で決める。調査と実装の多くは Claude Code に任せています。誤答・過抽出・抽出漏れといった症状ごとに分析のセッションを分けて並列で動かし、全セッションが読む前提（定義、数字の出し方、報告の単位）は自分が書きます。AI の結論には根拠のデータ行を示させ、別のセッションに独立して確かめさせて、裏付けの無いものは差し戻します。AI が 66 件に影響するとした不具合が、確かめると 1 件だったこともあります。

どの結論を採るかは自分が決め、判断の理由、採らなかった案、測った値は PR の本文に残します。

自分定義・測り方を書き、結論の採否を決める
↓
統括施策をまとめ、実行と採点を回す
↓
誤答の分析
過抽出の分析
抽出漏れの分析
↓
検証結論の裏を取り、誤りなら差し戻す

100 ラウンド超を回して、学習用データで精度 69.8% → 90.6%

08仕事の不便は、道具で減らす

自分とチームが繰り返す作業から。マージされた PR を毎週分類して Slack に投稿する仕組み（GitHub Actions）を作り、分類できなかった PR が見えるようにして、PR タイトルの決まりを 2 つのリポジトリの開発ガイドに入れました。評価を速く回す基盤（評価の高速化）も、施策を試すたびに数時間待つ不便から始まっています。

  1. マージされた PR を集めるGitHub Actions
  2. 種類ごとに分類する分類できない PR も見せる
  3. Slack に投稿タイトルの決まりを開発ガイドへ

09データベース・API の設計

パイプラインの出力を受け取る本番のデータベースと API（TypeScript・PostgreSQL）も担当しています。

A

店舗の手動登録：NULL を許して一意制約を残す

最短の直し方が、既存の安全網を素通りしないかを読む。

  • Google Maps の識別子が必須かつ一意なのに、手動登録では毎回同じ空文字が入り、2 件目から必ず失敗していた
  • ダミー値を入れる案は、識別子が空かどうかで判定する安全網 3 か所を素通りし、外部 API に課金付きの無効な要求を送ると分かって却下した
  • PostgreSQL の UNIQUE は NULL どうしを重複とみなさないので、識別子を NULL 可にし、一意制約は残した
詳しく読む
工夫
パイプライン側の入力の型が識別子を必須とし、未知のキーを拒否していたので、デプロイの順序をパイプライン → DB に固定し、5 本の PR に分けた。重複登録の検出は、数百万行に部分一致用の索引を新たに保つより、同じ店名での再申請を既存の索引が効く完全一致（入力を全角・半角の 2 通りにして照合）で拾う方が安いと判断した。
B

下流を止めない SNS のスキーマ移行

どの時点でも、旧カラムだけで動けるように移す。

  • SNS アカウントが 1 カラムの配列にまとまっていて、部分更新で Instagram だけが見つかると X が消えた
  • JSON の 1 カラムにまとめる案（取り出しが複雑で、型を DB で保証しにくい）と比べ、プラットフォーム別の 3 カラムを足した
  • 旧カラムは下流が読むので完全なリストとして残し、冪等で途中から再開できるバッチで値を写した
詳しく読む
課題
ロックと取得元の URL も SNS 全体で 1 つしか持てず、手で直した値が別の SNS の更新と一緒に上書きされた。
工夫
値を写すバッチ → 管理画面 → 検証ツール → 製造側の順に読み書き先を移した（expand / contract）。分類のドメイン判定も部分一致から末尾一致に直し、誤分類されていた 1,826 件の URL を是正した。
  • 3 つの取り込み経路で結果が違った住所の正規化を、4 段階に分けて 1 経路に寄せた。最後はパイプライン側が住所の構成要素を送る形に変え、DB 側の再正規化を不要にした。
