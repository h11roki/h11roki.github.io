LLM パイプラインの評価を、数時間から数分に

施策を 1 つ試すたびに数時間待っていた評価を、外部呼び出しの記録と再生で、ネットワークに触れず、毎回同じ結果で回せるようにしました。

2〜3 時間 → 約 8 分900 店舗の評価。これまでは 20 並列で 2〜3 時間かかり、外部サービスの状態で結果も揺れた。約 8 分は、100 店舗を 48 秒で採点した実測からの見込み
48 秒100 店舗を 8 並列で採点した実測。外への接続 0、毎回同じ結果

02記録して、ネットワークを塞いで再生する

本番と同じ処理を、外に出ずに何度でも流す。検索・クロール・LLM・住所の照合など、結果を左右する外部の呼び出しを一度だけ実際に呼んで記録します。評価のときはネットワークを塞ぎ、記録から結果を返して採点します。採点は PR ごとに CI のジョブでも回るので、変更のたびに同じ店舗で前後を比べられます。

  1. 記録する外部の呼び出しを 1 回だけ実際に呼ぶ
  2. 再生するネットワークを塞ぎ、記録から返す
  3. 採点する法人番号の一致で採点
  4. PR ごとに回すCI のジョブで、毎回同じ店舗で比べる

03照合のキーは「結果を決める入力」

URL ではなく、サービス・メソッド・入力で引く。先行の試作は HTTP の層で URL だけを照合していて、住所の照合サービスに別の住所を送った呼び出しに、前の住所の結果を返していました。記録の単位を外部サービスのクライアントにし、キーを（サービス、メソッド、結果を決める入力）にして、この取り違えが起きない形にしました。

LLM の記録のキーには、プロンプトのテンプレート（system・user・出力スキーマ）のハッシュも入れました。文言を 1 つ変えると、その呼び出しだけが記録から外れて取り直されることを確かめています。

照合のキー
キー結果
URL だけ（試作）別の住所の結果が返った
サービス・メソッド・結果を決める入力同じ入力にだけ同じ結果を返す
＋ プロンプトのハッシュ文言を変えた呼び出しだけ取り直す

04記録漏れを、静かな失敗にしない

止めるべきものは止め、一時的な失敗は固めない。既存のコードには「例外を受けて既定値に戻る」処理が多く、記録に無い呼び出しがそこで飲み込まれると、取得の失敗として扱われ、精度の変化に見えてしまいます。記録に無いことを知らせる例外は BaseException の子にして、必ず止まるようにしました。

一方で、503 やタイムアウトのような一時的な失敗は記録に固めず、その店舗を「不完全」として次の取り直しで取ります。既存の採点（TypeScript・テスト 0 件）は Python に移し、規則ごとにテストを書きました。

呼び出しの扱い
場合扱い
記録に無い呼び出しその場で止める（BaseException の子）
一時的な失敗（503・タイムアウト）記録せず、その店舗を取り直す
サイトが返したエラーページ中身として記録する

05届いていない分は、内訳を測って次の手を決める

目標の 1 分に、CI では 79 秒。手元では 20 店舗を約 30 秒で回せますが、CI では 79 秒で、目標の 1 分に届いていません。内訳をタイマーで積算すると、時間の 62% が HTML の構文解析で、そのうち 65% が同じ HTML の解析し直しでした。並列を 8 から 12 に増やしても速くならなかった（CPU を取り合う）ので、次は解析結果を使い回す改修を狙います。

CI での 1 回の評価79 秒　目標は 60 秒
  • 約 40%同じ HTML の解析し直し（構文解析の 65%）。次の改修はここを狙う
  • 約 22%そのほかの HTML の構文解析
  • 38%それ以外

最初は「時間の 8 割が 1 つの関数」とレビュー用の資料に書いていましたが、プロファイラの上乗せによる誤りでした。タイマーで測り直すと 2 割で、レビューに出す前に直しました。

06実データで回して、不具合を潰す

作った仕組みを、まず自分で疑う。本番のデータで回すと、記録と再生の仕組み自体の不具合が見つかりました。

見つけた不具合と直し方
不具合直し方
ページ本文の Unicode の行区切り（U+2028）で、記録の行が途中で切れる改行（\n）だけで分けるよう修正
再生用のプロセスが、import の時点でクラウドのメタデータへ接続しに行く再生中は外に出ないよう修正
レビューを待つ 1 週間で開発ブランチが 32 コミット進み、参照マスタの読み込みが変わった記録の位置を読み込み関数の外側に移して 7 本を載せ直し、足りない呼び出しだけを取り直した（232 秒）
＋

評価の全件実行で、結果が欠ける

相手の障害も、こちらの弱さも、両方直す。

  • 評価用の全件実行（200 店舗ずつ投入）で、1 回分の 200 店舗中 35 件の結果が欠けた
  • 社内のクロール用 API が接続を受け付けなくなっていること（TCP 接続の 18.3% で SYN に応答なし）を、開いたポートと閉じたポートへの同時接続で 1 分で特定し、担当者に報告した
  • こちら側も、長いタイムアウトが接続確立にまで掛かってリトライが働いていなかったので、接続と応答待ちのタイムアウトを分け、止まっても実行全体が止まらないようにした
