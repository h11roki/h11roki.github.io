個人開発 ・ 2026.10– ・ 本番公開中

shirube（道標）
なりたい職業から、卒業までの時間割を組む

職業名を入れると、LLM が必要なスキルを読み取り、シラバスを埋め込み検索して候補を集め、LLM が候補を読み直して理由つきで授業を選び（RAG と LLM によるリランク）、学期ごとの時間割に並べます。一人で設計し、本番に公開しました。改善を始める前に、精度・揺れ・費用を測る評価の仕組みを作り、変更を採るかどうかはそれで決めています。

02背景と目的

履修を選ぶとき、シラバスを 1 つずつ読んでも、その授業が将来の仕事のどこで役に立つのかは分かりにくく、時間割の重なりも自分で確かめる必要があります。しかも職業と授業は使う言葉が違う（データサイエンティストと確率統計など）ので、キーワード検索ではつながりません。

shirube は、なりたい職業から逆算して、シラバスの中身を根拠に授業を選び、選んだ理由を添えて、卒業までの学期ごとの時間割に並べます。最初の対象は自分の学科で、公開シラバス 530 ページを取り込みました。

03主な機能

  • 職業の中心になる授業（柱）と、その前提になる授業（礎）を選び、授業ごとに理由とシラバスの原ページへのリンクを付ける。
  • 残りの学期に、配当回生、開講学期、コマの重なり、1 学期 16 単位の上限を守って並べる。路線図と週の時間割表で見られる。
  • 作成には 10〜30 秒かかるので非同期のジョブにし、作成中は 4 つの段のどこまで進んだかと待ち時間を出す。ページを閉じても作り続ける。
  • 曖昧な職業名は、どう読んだかを画面に出す。もう取った授業は覚えて候補から外す。スマホ幅でも使え、WCAG 2.2 AA を目安にした。

04成果

最初の基準と改善後の設定を、同じ時間帯に交互に流して比べました。費用を変えずに、関係のない授業を減らし、作り直したときの揺れを小さくしました。

その後、柱の理由に「仕事のどこで使うか」を書かせる変更で、理由が具体的な柱の割合を 36.8% から 67.1% に上げました（開発用 50 職業、差の 95% 区間 +17.8〜+42.7 ポイント）。測る前に採る条件を決めた変更は 9 件で、6 件を採り、3 件は採りませんでした（下の表）。

技術面の特徴

  1. エージェントにはせず、読み取り（LLM）、検索（埋め込み）、選び直し（LLM）、配置（アルゴリズム）の 4 段に固定した。期待する授業をどの段で落としたかまで数えられる。
  2. 評価データ（開発用 50 職業、ホールドアウト 20 職業）と比べる道具を先に作り、採る条件は変える前に ADR に書いてから測った。
  3. 3 回の多数決で誤りと揺れを減らし、増えた費用は候補の絞り込み、入力キャッシュ、読み取りの使い回しで戻した。
  4. 公開を前提に、1 日の上限、前払い、候補に無い授業を返せない構造化出力、15 分ごとの外からの監視を入れた。

05処理の流れと構成

推薦は、エージェントにはせず、読み取り（LLM）、検索（埋め込み）、選び直し（LLM）、配置（アルゴリズム）の 4 段に固定しました。期待する授業をどの段で落としたかまで数えるためです。

FastAPI（クリーンアーキテクチャ）、Next.js、PostgreSQL + pgvector、AWS EC2 と Docker Compose、GitHub Actions。各枠の番号は、判断を記録した ADR です（押すと GitHub で読めます）。

  3. 埋め込みtext-embedding-3-large、1536 次元。同じ本文は計算し直さない00150063
  4. PostgreSQL + pgvector科目、チャンク、埋め込み。本番へは科目の表だけ移す

受け付け

  1. 画面（Next.js）Google でログイン。利用者番号入りの短い JWT を付けて転送00270039

推薦worker

  1. ① 読み取りgpt-5.4-mini。職業名を解釈、前提、スキル 3〜6 個に直す。職業名ごとに使い回す00180052
  2. ② 検索pgvector。職業全体とスキルごとのクエリの順位から交互に 20 件。全件を厳密に計算0063
  3. ③ 選び直しgpt-5.4-nano × 3。候補の抜粋を読み、柱と礎を理由つきで返す。3 回並列に呼び、2 票以上を残す00230049
  4. ④ 配置自作のアルゴリズム。回生、学期、コマ、16 単位の上限を守り、貪欲法で詰める。LLM は使わない00070025

推薦キャッシュ（7 日）：職業名と条件、モデル、プロンプト、コードの指紋が同じなら ①〜③ を飛ばし、LLM を呼ばずに作る。コードを変えると前の結果は当たらなくなる0092

  • デプロイCI がすべて通った版だけサーバーが取りに行く。応えなければ前の版に戻す0094

06プロンプトとコンテキストの設計

どちらの呼び出しも、LangChain の構造化出力（json_schema、strict）で呼んでいます。

①

読み取り（gpt-5.4-mini）

入力
役割（進路の相談役）。学科の授業がそのまま備える職業はそのまま読み、細かい職種だけ広く読むという決まり。利用者の職業名。
出力
職業名の解釈、前提（無ければ null）、スキル 3〜6 個（20 字以内の名詞句）。
工夫
スキルは製品名ではなく、授業で学ぶ分野の名前で書かせ（React ではなく「Web の仕組みとプログラミング」）、検索のクエリをシラバスの言葉に寄せた。前提を書かずに言い換えた答えは、コードで元の職業名に戻す。
③

選び直し（gpt-5.4-nano × 3）

入力
柱と礎の定義と選ぶ順。職業、前提、スキル。候補 20 件の抜粋（概要 450 字、到達目標 250 字、各回のテーマ 350 字）。
出力
科目名と、前提にする柱は、候補の列挙（enum）に限る。理由は 80 字以内。
工夫
抜粋の切り方を、正解を作った判定者と同じにし、入力の違いが評価に混ざらないようにした。抜粋に無いことは書かせない。2 票目を 0.5 秒遅らせて、入力キャッシュに当てる。

07技術選定と設計の判断

どれも、測った値か、試した結果から決めました。

判断理由
エージェントにせず、段を固定したワークフローにするエージェントにすると、どこで誤ったかを分けて測れない。段ごとに指標を持たせた。LLM の出力を道具の呼び出しや DB の問い合わせに使わないので、プロンプトインジェクションの影響も画面の文で止まる
検索で絞ってから、LLM が読み直す検索の上位 10 件の約 2 割は、判定で関係なし。LLM が中身を読めば外せ、理由も根拠を持って書ける。全科目を読ませると入力が 5 倍以上になり、他の学科に広げられない
段ごとにモデルを分ける読み取りは、曖昧な職業名 4 件で前提を書けたのが mini は 4 件、nano は 1 件だったので mini。選び直しは 10 職業 × 2 回で nano が mini と同等以上、費用は約 4 分の 1 なので nano
スキルごとのクエリで検索する（クエリ分解）取りこぼしの多くは、スキルが 1 つのクエリの中で薄まることが原因だった。50 職業で交互に比べ、関係なしが 23.0% から 15.1% に下がった（p = 0.001）
時間割は貪欲法、作成は非同期LLM に組ませるとコマが重なる。同期で作ると、画面がタイムアウトしたあとに保存され、作り直しで費用が二重にかかる

08直面した課題と解決

01

LLM の答えが揺れ、関係のない授業が混ざった

課題
最初の基準では、関係なしが 23%、作り直したときの重なりが 0.45 だった。
解決
選び直しを 3 回並列に呼んで 2 票以上だけ残すと、関係なしは 10% に下がったが、費用は 0.81 円から 1.57 円に増えた。そこで候補を 30 件から 20 件に絞り（1.14 円）、2 票目を遅らせて入力キャッシュの当たりを 50% から 63% に上げ（1.01 円）、職業の読み取りを使い回した。最初の基準と交互に流して比べると、同じ 0.83 円のまま、関係なしは 27.6% から 21.6%、重なりは 0.52 から 0.72 になった。
02

公開すると、費用を使い込まれるおそれがあった

課題
はじめは失敗した道標を 1 日の上限に数えていなかった。職業名に指示を混ぜてわざと失敗させれば、上限なしに費用を使えると見直しで気づいた。
解決
失敗も上限に数えるように直した。出力は enum で候補の授業に限り、道標は本人にしか見えない（他人の道標は 404）ので、混ぜられた指示の影響は本人の画面に閉じる。指示を混ぜた職業名 3 件を流して、指示に従わず、候補に無い授業も API キーも出ないことを記録し、指示文かモデルを替えるたびに流し直している。

09評価の仕組み

LLM の出力はもっともらしく見えるので、感覚ではなく数字で採否を決めるために、改善の前に作りました。

  1. 評価データ開発用 50 職業、ホールドアウト 20 職業
  2. 交互に流す2 つの設定を、職業と回ごとに交互に流す
  3. 比べる並べ替え検定と区間。どの段で落としたかも数える
  4. ADR採る条件は測る前に書く。採らない判断も残す
  5. ホールドアウト直しを決めたあとに 1 回だけ、平均と検定だけ見る

正解の作り方

職業ごとの正解は無いので、Claude のサブエージェント 3 体（採用担当のエンジニア、カリキュラムを作る教員、進路を考える 3 回生）が、候補の授業を「中心・土台・関係なし」で独立に判定した多数決にしました（LLM-as-a-Judge）。期待する授業は開発用で 151、ホールドアウトで 58 です。アプリが使う OpenAI とは系統を分けています。

理由の文は、具体的・ぼんやり・無しの 3 段で同じ 3 体が判定しました（柱の理由での一致は Fleiss の κ 0.80）。安く回すため gpt-5.4-nano と mini で判定器も作りましたが、ホールドアウト 75 件で Cohen の κ が 0.54 と、事前に決めた 0.6 に届かなかったので採りませんでした。

ホールドアウトは評価データに印を持たせ、実験の道具が職業ごとの結果を出さないようにして、うっかり中身を見る事故を防いでいます。

評価の作り方を直したこと

  • A/A テストで偽の差が出た。同じ設定どうしでも、ブートストラップの区間では 10%（名目の 5% の 2 倍）で差ありと出た。職業ごとの並べ替え検定に替えると 5% に収まった。
  • 流した時刻で結果がずれた。同じ設定とコードでも、別の時刻に流すと関係なしが 9 ポイントほど動いた。2 つの設定を職業と回ごとに交互に流し、時刻のずれを差から除いた。
  • 開発用に合わせ込んでいた。検索の改善は、直しを決めるときに見た 30 職業では候補の再現率が 6.4 ポイント上がったが、あとで足した 20 職業では 1.2 ポイント下がった。そこでホールドアウトを別に取っておくことにした。

まだ足りないこと

  • 正解は LLM の判定者 3 体の多数決で、人の判定との一致はまだ測っていない。
  • 学生にはまだ使ってもらっておらず、役に立つかは確かめていない。
  • 柱の適合率が 37〜42% と低い。網羅を優先して、柱を広く選ぶようにしたため。
  • 必修、卒業要件、前提科目の順序は見ておらず、対象も 1 学科だけ。

次にやること

  • 学科の学生や教員に一部を判定してもらい、Claude の判定者との一致（κ）を測る。
  • 期待する 151 件のうち、選び直しで落としたのが 13%、読み取りで 12%、検索で 3%。次は読み取りの揺れを直すが、同じ 50 職業で直し続けると合わせ込むので、見ていない職業を足してから確かめる。
  • 履修登録の時期（3〜4 月）に学生に使ってもらい、作り直しの回数や、もう取ったと答えた授業を、作成の記録と合わせて見る。
  • 必修と卒業要件を入れ、時間割を整数計画に替える。先に、貪欲法で要件を満たせない道標の数を測る。

展望

  • ほかの学科・学部、ほかの大学に広げる。今の対象は自分の学科だけ。検索で候補を絞ってから LLM が読み直す形にしたのは、全科目を読ませると入力が 5 倍以上になり、対象を広げられないからで、広げることを前提に作っている。
  • モバイルアプリも始めたい。今の Web 版もスマホ幅で使えるが、アプリとしても届けたい。
