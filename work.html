トップ / 仕事 / 精度改善

Baseconnect 株式会社 ・ 長期インターン ・ 技術的にいちばん苦労した開発経験

店舗の運営会社を特定する LLM パイプラインの精度改善と、評価の作り直し

営業向け企業データベースでは、営業の連絡先は店舗ではなく、その店舗を運営する会社にあります。運営会社を Web 調査と LLM で特定する本番のパイプラインを改善しました。違う会社を出すと、営業は意思決定者のいない会社に連絡してしまうので、誤りを増やさないことを最優先にしました。

69.8% → 90.6%精度（改善に使った 879 店舗）
63.6% → 77.9%カバレッジ（一度も使っていない 200 店舗。本番に入っていた値と比較）
136 → 44 件違う会社を出した件数（879 店舗）

01概要

期間
2026 年 8 月〜10 月（インターン自体は 2026 年 4 月から）
技術
Python、Dagster、社内 GPU でホストした LLM（Qwen 系の 35B MoE）、形態素解析（UniDic）、検索 API・クローリング、PostgreSQL、AWS（SQS・S3）、Parquet・DuckDB、GitHub Actions、Claude Code
体制
エンジニア約 10 名のデータ基盤チーム。店舗データ（数百万件規模）を社員エンジニア 1 名と 2 人で担当。正解データの作成は QA 担当、コードレビューは社員エンジニアが行う。変更はテストを付けて小さな PR に分け、レビューを受けてマージする
役割
既存の本番パイプラインの精度改善と、評価の作り直しを主に担当（分析・設計・実装・検証）。採点の基準も自分で作った
参考 URL
社内のコードのため公開していません（社内システム名・店舗名は伏せています）

02開発内容

店舗ごとに Web を検索し、取得したページを LLM に読ませて、運営会社を法人番号の 1 社まで特定する本番パイプライン（データベースの数十万店舗に運営会社を供給）の精度改善を任されました。目標は精度・カバレッジともに 95% でした。

  1. 検索・取得店舗名と住所で Web を検索し、ページを取得
  2. 候補の抽出ページから社名の候補を切り出す
  3. LLM の判定候補のうち運営会社はどれかを判定
  4. 名寄せ社名を法人番号の 1 社に決める
  5. 登記の照合閉鎖・合併した法人を除く

03結果

改善に一度も使っていないテスト用の 200 店舗で、本番に入っている値と比べました（区分の分け方は下の 04）。精度はほぼそのままに、カバレッジを 14 ポイント上げています。

04苦労したこと・工夫したこと

01

直営か加盟店か、同名の別法人か

社名が読めても、それが運営会社とは限らない。

  • 採点を、社名ではなく法人番号の一致に変えた
  • LLM に判断材料（住所に登記された会社、社名が載っていた欄、ページのドメイン）を渡し、「読んではいけない会社」を明文化した
  • 名寄せは完全一致の社名を優先し、同点なら店舗の都道府県で絞った
  • 採った法人を国税庁の公表データで照合し、閉鎖は出さず、合併は承継先に寄せた
詳しく読む
課題
チェーン店は本部の直営店と加盟店（フランチャイズ）が混ざり、加盟店で本部を出すと誤りになり、直営のブランドで加盟店に寄せても誤る。社名が読めても、同名の別法人、「〇〇ホールディングス」と事業会社、閉鎖・合併した法人の中から 1 社に決める必要がある。しかも評価は社名で採点していて、同名の別法人を出しても正解に数えていた。
工夫
ブランドから本部を即答する層は、即答した 119 件がすべて正しいことを全数で確かめて残し、即答できない店だけをページから判定した。LLM には、ページ上のどの欄の社名か（「運営会社」か「募集主」か）も渡した。名寄せは「ホールディングス」との差を別に扱い、同名の候補が 1 社だけなら都道府県で絞らず、本社が別の県にある全国チェーンを落とさないようにした。加盟店の扱いは正解データの作成者と基準をすり合わせた。ページだけでは決めきれない型は、ブランドのマスタに本部の直営割合を持たせれば止められると示して引き継いだ。
02

誤りの原因を切り分ける

直す場所を、誤りの件数で決める。

  • 記録に、値を消した段・LLM が退けた候補の理由・例外の実際の型・コードの版を足した
  • 誤りを 4 つの原因に機械的に分け、件数の多い所から直した
  • 出力形式を変えた自分の変更 2 件が解析失敗を 8 → 364 件、2 → 29 件に増やしていたので撤回し、JSON の型を生成時に強制しない呼び出しが原因だと突き止めた
  • 採否は「増える正解」と「新しく生む誤り」の両方で決めた（正解 74 件に誤り 230 件の案は採らない）
詳しく読む
課題
判定の記録は残っていたが、どの段で値を消したか、例外の本当の型（リトライの例外に包まれて消えていた）はログにしか無く、誤りを段階別に数えられなかった。その中で、LLM の出力形式を変えた自分の変更 2 件が、応答の解析失敗を増やしていた。2 件目は誤答の増減だけを見て、一度採用していた。
工夫
誤りを「材料が無い／候補にしていない／判定で落ちた／別の法人になった」に機械的に分けて、直す場所を件数で決めた。自分の変更 2 件は、同じ原因で説明できるはずだと考えて呼び出し側の設定を読み、原因を突き止めた。以後、変更は解析失敗と、正解 → 誤りを含む全方向の動きで判定し、出力の順序はテストで固定した。
03

改善が本物か、揺れか分からない

揺れを測ってから、効果を数える。

  • コードを変えずに流し直すだけで、28〜40 店舗の結果が入れ替わった
  • 検索結果をキャッシュで固定した
  • LLM は本文が同じ 338 ページで判定の反転 0 件を実測した
  • 効果は、取得したページが前後で同じ店舗だけで数えた
詳しく読む
課題
1 つの施策で動くのは数件なので、全体の精度で採否を決めると、効かない施策を採ってしまう。
工夫
temperature 0 でも GPU の推論は揺れうるので、LLM の判定が変わらないことは前提にせず実測した。残る揺れはページの取得だと分かったので、施策の効果は、取得したページが前後で同じ店舗だけで数えた。
04

改善に使った店舗に、合わせ込んでいた

改善に使っていない店舗でも通る規則だけを残す。

  • 自分が入れた出典のない 14 行の表が精度の約 2pt を作っていた。本番では根拠なく約 4,400 店舗の答えを変えるので、数字が下がるのを承知で外した
  • 本番から抜き出した 1,800 店舗を、開発用・検証用・テスト用（最後に 1 回だけ測る）に分けた
  • 規則は「その店舗のための例外」ではなく「同じ型の店舗に効く条件」で書き直した
  • まったく違う会社を出す誤りには、値を採ったページでその会社の立場を LLM に聞く、最後の検査を入れた
詳しく読む
課題
14 行の表を外しても、新しい 400 店舗で測り直すと精度は 62% だった。外れた 50 件を 1 件ずつ見ると、改修前からの誤りが 36 件、改善で足した規則が別の店舗で外れたものが 14 件だった。
工夫
1,800 店舗は難しさの偏りをそろえて、開発用（1,000 店舗。中を見て規則を考える）・検証用（600 店舗。件数だけを見る）・テスト用（200 店舗）に分け、開発用と検証用の両方で、増える正解と新しく生む誤りを数えて採否を決めた。最後の検査は、モールの管理会社、別の会社の求人広告、隣の店のインボイス番号などを出す誤りが対象で、施設の管理会社・別の店・広告と読めるときだけ値を捨てる。迷うときは値を残す方に倒し、当て直して正しい答えを 1 件も捨てないことを確かめた。マスタの値が原因の誤りはコードで上書きせず、マスタの担当者に修正を依頼した。

目標の 95% には届きませんでした。誤答と抽出漏れの 69 件を本文と 1 件ずつ突き合わせると、実装で動かせると確かめられたのは 7 件でした（正しい社名がページに無いのが 18 件、候補にあるのに採れていないのが 29 件など）。構造的な不足だと上長に示して区切り、届かせる条件と原因別の件数をつけて引き継ぎました。

05この経験から

LLM のように確率的に間違うシステムでは、まず「何を、どう測れば本番で正しいと言えるか」を決めることがいちばん大事だと学びました。改善に使った店舗で 90% と出ても、それは本番の精度ではありませんでした。今は、数字が上がったときほど理由を確かめ、根拠が無ければ自分の変更でも外します。

この改善は、施策を 1 つ試すたびに数時間待つ評価で回していました。その不便から、次に評価を速く回す基盤を作りました（評価の高速化）。
