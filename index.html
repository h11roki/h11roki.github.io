01仕事

本番の LLM を、誤りを数えて直す

Baseconnect 株式会社（営業向け企業データベース）で、AI エンジニアとして長期インターンをしています。店舗データを作る本番の LLM パイプラインと、それを受け取るデータベース・API の両方を書いています。

店舗の運営会社の特定精度

69.8%→90.6%

改善に使った正解データ付きの 879 店舗。社名ではなく法人番号の一致で採点

カバレッジ（改善に一度も使っていない店舗）

63.6%→77.9%

テスト用の 200 店舗で、本番に入っていた値と比較。精度は 89.1% → 89.6% とほぼ同じまま

違う会社を出した件数

136 件→44件

879 店舗で。運営会社の無い店舗に会社を出した「過抽出」も誤りに数える。少ないほど良い

評価にかかる時間（900 店舗）

2〜3 時間→約8分

約 8 分は、100 店舗を 8 並列で 48 秒だった実測からの見込み（これまでは 20 並列）。外部呼び出しの記録と再生で、ネットワークに触れず、毎回同じ結果で採点

エンジニア約 10 名のデータ基盤チームで、数百万件規模の店舗データを社員エンジニアと 2 人で担当しています。

  • いちばん苦労した開発経験
  • 評価の高速化
  • 仕事の進め方

社内のコードのため、ソースコードは公開していません。社内システム名・店舗名は伏せています。

  1. 店舗の運営会社を特定する LLM パイプラインの精度改善いちばん苦労した経験

    誤りを段階別に数える記録を足して直す場所を件数で決め、結果の揺れから施策の効果を切り離して測った。改善に使った店舗への合わせ込みに気づき、評価用の店舗を分け直した。5 本の PR に分けてレビューを受け、本番にマージ。

  2. LLM パイプラインの評価を、数時間から数分に

    検索・クロール・LLM の呼び出しを記録し、ネットワークを塞いで再生・採点する CLI と CI のジョブを設計・実装した。プロンプトを変えた呼び出しだけが取り直される。7 本の PR に分けてレビューを受けた。

  3. データの誤りを直し、同じ誤りを二度と入れない

    店舗の属性の抽出で、開業日の精度を 45.7% → 90.4%、決済手段を 47.0% → 90.8% に（社内の精度検証）。既存データの修正と、取り込み時のガードを必ず組で入れている。

  4. 本番データベース・API の設計と移行

    TypeScript・PostgreSQL。下流を止めずに進める段階的なスキーマ移行、取り込み API の設計、一意制約で失敗していた店舗の手動登録の修正など。

03進め方

測り方を先に決めて、判断は残す

LLM の出力はもっともらしく見えるので、感覚ではなく数字で採否を決めています。仕事でも個人開発でも同じ進め方です。

測り方を、直す前に決める

改善を始める前に、評価データと比べる道具を作ります。採る条件は、測る前に書いておきます。

shirube　何も変えていない設定どうしでも「差あり」が名目の 2 倍出ると気づき、2 つの設定を交互に流して並べ替え検定で比べるように直した。

数字が上がったときほど、疑う

改善に使ったデータで上がった数字は、本番の精度とは限りません。理由を説明できない改善は採りません。

インターン　自分たちが入れた出典のない 14 行の対応表が精度の約 2pt を作っていた。本番では根拠なく約 4,400 店舗の答えを変えるので、数字が下がるのを承知で外した。

自分の変更でも、測って戻す

増えた正解だけでなく、新しく生んだ誤りも数えて採否を決めます。PR には「正解 +16 ／ 誤り −2」のように両方を書きます。

インターン　LLM の出力形式を変えた自分の変更 2 件が、応答の解析失敗を 8 → 364 件、2 → 29 件に増やしていた。撤回して、JSON の型を強制しない呼び出しだったという共通の原因を突き止めた。

判断を、文章で残す

設計の選択肢と、採らなかった理由を、実装より先に ADR（設計判断の記録）に書きます。

shirube　ADR は 99 本（2026 年 11 月 8 日時点）。採らなかった改善 3 件も、数字と理由を残している。

速さは AI に、正しさの責任は自分に

インターンでは、Claude Code の複数のセッションを、統括・症状別の分析・結論の検証に役割を分けて並列で動かし、100 ラウンドを超える改善を回しました。自分は、全セッションが従う定義・測り方・報告の単位を書き、どの結論を採るかを決める役に徹しました。

AI の結論には根拠のデータ行を示させ、裏付けのないものは差し戻します。AI が 66 件に影響するとした不具合が、確かめると実際は 1 件だったこともあります。

仕事の進め方を詳しく
自分定義・測り方を書き、結論の採否を決める
↓
統括施策をまとめ、実行と採点を回す
↓
誤答の分析
過抽出の分析
抽出漏れの分析
↓
検証結論の裏を取り、誤りなら差し戻す
